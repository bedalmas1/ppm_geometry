### Phase 2 — Dataset pipeline — DONE
Full write-up: [`paper/dataset_selection.md`](./paper/dataset_selection.md) — real, computed statistics for all 5 datasets, not literature figures.

**Dataset roster (finalized, downloaded, processed):** BPIC12, BPIC17, BPIC19, Sepsis, Helpdesk — all 5 downloaded (`data/raw/`, gitignored) from verified 4TU.ResearchData direct links (exact byte-size match confirmed for every file, nothing guessed) and run through the pipeline into `data/processed/<dataset>/{train,val,test}.parquet` + `manifest.json`. Every case/event/activity count matches the literature exactly (e.g. BPIC12: 13,087 cases/262,200 events; BPIC19: 251,734 cases/1,595,923 events/42 activities). **Data-quality finding, not yet resolved:** BPIC19's computed temporal span starts 1948-01-26 — a known data-quality artifact (placeholder timestamps on a handful of events), not a real 72-year process or a pipeline bug; needs an explicit cleaning rule before Phase 3 training.

**Pipeline implementation:** `src/data/` is now a proper Python package (`schema.py` canonical case_id/activity/timestamp columns, `loaders.py` — XES via `pm4py`, CSV for Helpdesk, both converging to the same schema, `splits.py` — time-based case-sort split with a sha256 provenance hash, `stats.py` — full spec §6 descriptive-stats list). Driven by `scripts/prepare_dataset.py` (config-driven, one YAML per dataset in `configs/datasets/`, `--all` flag to run everything). 18 unit tests (`tests/test_loaders.py`, `test_splits.py`, `test_stats.py`) validate the splitting/stats logic against synthetic data with hand-computed expected values — pass without needing the real (gitignored) datasets. Caught and fixed a real Windows-only bug along the way: `Path.read_text()`/`write_text()` without `encoding="utf-8"` silently mojibake's non-ASCII characters (em dashes, §) on this locale — fixed in `scripts/prepare_dataset.py`.

**Major environment finding — Python 3.13 → 3.12:** the dependency-group smoke test (see below) discovered TensorFlow 2.19.1 ships no wheels for CPython 3.13 (cp311/cp312 only). Since A1/A2 need TensorFlow, **the whole project was switched from Python 3.13.0 to 3.12.10** (`.python-version`, `pyproject.toml`'s `requires-python` now `>=3.11,<3.13`) — every other framework in the roster supports 3.12 fine, so one shared Python version was kept rather than fragmenting per framework.

**Dependency-group smoke test — all 4 groups (`tf`, `torch`, `torch-hf`, `torch-dgl`) now genuinely verified working** (installed AND actually imported AND ran a basic operation, not just "pip install succeeded"). This surfaced and fixed a chain of real, non-obvious issues, in order:
1. TF/CPython 3.13 incompatibility (above) → switched to Python 3.12.
2. `torch-dgl`: dgl==2.2.1's PyPI wheel bundles a **precompiled C++ `graphbolt` extension for specific torch builds only** (inspected the wheel directly: 2.1.0–2.1.2, 2.2.0–2.2.2, 2.3.0 — nothing newer). The unpinned `torch>=2.3` constraint resolved to whatever the latest available torch was and failed at import with a missing-DLL error. **Fixed: pinned `torch==2.3.0`, `dgl==2.2.1` exactly.**
3. dgl's `graphbolt` module imports `torchdata.datapipes`, an API **removed** in newer torchdata releases (confirmed: torchdata 0.11 raises `ModuleNotFoundError`). **Fixed: pinned `torchdata==0.7.1`**, the last release still shipping it.
4. dgl's compiled extensions were built against NumPy 1.x; NumPy 2.x triggers ABI warnings. **Fixed: `numpy<2` added to the `torch-dgl` extra.**
5. dgl's `graphbolt.impl.ondisk_metadata` imports `pydantic` at runtime but doesn't declare it as a dependency — a packaging bug in dgl itself. **Fixed: `pydantic` added explicitly.**
6. **A structural fix, not just a pin:** uv resolves ONE universal lockfile satisfying every optional-dependency group simultaneously by default. `torch-dgl`'s necessary `torch==2.3.0` pin was silently bleeding into `torch-hf`, breaking `transformers` (which self-disables its PyTorch backend under torch<2.5 — a runtime check, not a declared packaging constraint, so uv had no visibility into the conflict). **Fixed properly: added `[tool.uv] conflicts` declaring `tf`/`torch`/`torch-hf`/`torch-dgl` mutually exclusive**, so uv resolves an independent version set per extra instead of one shared set — matches reality, since no training run ever needs two of these frameworks at once.
7. Even with conflicts declared, `torch-hf` still needed an explicit `torch>=2.5` floor added to its own extra (the resolver has no data-level reason to pick a newer torch than the declared minimum, since `transformers`' real requirement is invisible to it).

Final state: `tf` → TensorFlow 2.19.1 (Python 3.12, standalone). `torch` → torch 2.13.0 (current, for A4/A5/A7/B1/B2). `torch-hf` → torch 2.13.0 + transformers 5.15.0 (fully functional, not self-disabled). `torch-dgl` → torch 2.3.0 + dgl 2.2.1 + torchdata 0.7.1 + numpy<2 + pydantic (isolated fork, doesn't affect the other three groups). Base env (no extras) + all 18 tests confirmed green after every change.

### Phase 3 — Baseline reproduction — IN PROGRESS (8 of 9 models: A1, A2, A3, A4, A5, A6, A7, B1 done)
Full write-up: [`paper/phase3_baseline_reproduction.md`](./paper/phase3_baseline_reproduction.md) — updated per-model as each one is integrated; this section is a summary only.

**Execution strategy decided with the user:** training runs are **sequential**, never parallel, because this machine has only one GPU (NVIDIA RTX A2000, 8GB — confirmed via `nvidia-smi`; 20 CPU cores also available). Running multiple models on the same GPU simultaneously would contend for the same 8GB VRAM and corrupt the empirical compute-timing measurements Phase 2 flagged as still needed. Non-compute code work (adapters, config wiring) can be drafted in parallel; actual training cannot.

**A1 ProcessTransformer — DONE, pilot for the whole approach.** Vendored the architecture only (`src/models/process_transformer/model.py`, Apache-2.0, license file preserved alongside) — deliberately did **not** reuse the original repo's own `data_processing.py`, since that does its own train/test split and vocab-from-combined-data, which would violate spec §6's "identical splits across every model" requirement. Instead wrote `src/models/process_transformer/adapter.py` converting this project's own Phase-2 split parquet into the model's expected tensors, replicating the original's exact prefix-generation semantics. Config-driven training entrypoint: `experiments/train_process_transformer.py`.

Result: trained end-to-end on Helpdesk. Best validation accuracy 86.9% (paper reports 85.63% — close), but test accuracy only 72.9% micro / 63.2% macro-across-k — a real, disclosed gap, most likely from (a) training instability at the paper's stated lr=0.01 (visible loss spikes/recoveries during training) and/or (b) genuine temporal distribution shift under this project's strict chronological split (test is a truly later time period than train/val, unlike a random split which would leak future patterns). Not further hyperparameter-tuned — the pilot's actual goal (validate the full data→train→checkpoint→metrics→provenance pipeline) was met. **Notable independent validation**: reading the actual ProcessTransformer paper (fetched and read directly, not from memory) showed its Table 1 Helpdesk statistics (4,580 cases, 21,348 events, 14 activities, avg length 4.66) match this project's own Phase 2 pipeline output exactly — strong evidence the Phase 2 preprocessing is correct. Confirmed the vendored model's `prefix_representation` (GlobalAveragePooling1D) layer is retrievable by name post-training, ready for Phase 4's z_t extraction without touching the model file again.

**A2 Camargo GenerativeLSTM — DONE.** The original architecture is far more involved than A1's (3 input branches, pretrained/frozen embeddings, role clustering, a 2000-model hyperparameter search across 3 architecture variants). Scoped down consistently with A1's precedent: implemented **only the activity branch** of `model_shared_cat` (embed → LSTM → BatchNorm → LSTM(`prefix_representation`) → Dense-softmax), trainable (not pretrained/frozen) embeddings, no role branch (this project's schema doesn't carry resource data — keeping every model's input data identical, spec §6), fixed hyperparameters taken directly from the repo's own `dg_training.py` defaults (not guessed). The "insecure HTTP dependency" flagged in Phase 1 turned out to be moot: the repo vendors its own `support_modules/` locally, which is what actually gets imported — no external install ever needed.

Refactored the prefix-generation logic shared between A1 and A2 into `src/data/prefixes.py` (verified via regression check that A1's numbers didn't change).

Result: trained on Helpdesk, same split as A1 (confirmed identical `dataset_split_hash`). Best validation accuracy 81.8% (smooth, stable training — unlike A1's), but test accuracy only 63.5% micro / 59.1% macro-across-k. Two real comparison points found (fetched and read the actual Camargo BPM 2019 paper, not from memory): the paper's own Table 4 reports 78.9% on Helpdesk; a third-party re-implementation cited by ProcessTransformer's paper reports 76.51%.

**Notable cross-model finding:** the same validation-vs-test gap that appeared for A1 (Transformer, unstable training) reappears for A2 (LSTM, smooth training) — on the identical data split. Since two architecturally different models with very different training dynamics show the same pattern, this is stronger evidence for **genuine temporal distribution shift** under this project's strict chronological split than for an A1-specific optimization artifact. Both models' validation accuracy also meets or exceeds the original papers' own reported numbers — suggesting the stricter split is surfacing a real generalization gap that looser/ambiguous split methodologies in the original papers may not have exposed. This is being watched as a potential genuine methodological finding, not just a reproduction caveat (see Open questions).

**A4 SuTraN — DONE, first full-suffix model.** Original architecture is a multi-task encoder-decoder (activity + timestamp suffix + remaining runtime). Scoped to **activity-only** — stricter than the repo's own "NDA" variant, since NDA's timestamp *inputs* at inference are themselves autoregressively generated from the model's own timestamp *predictions*; dropping the prediction head while keeping the inputs would be architecturally broken. Every model in the roster now predicts activities only, a deliberately homogeneous target family, not a per-model cut. Core Transformer blocks (attention, FFN, encoder/decoder layers) vendored unmodified from `SuTraN/layers.py`; hyperparameters (`d_model=32`, 4 encoder + 4 decoder layers, 8 heads, `d_ff=128`, `AdamW(lr=0.0002)`, `ExponentialLR(gamma=0.96)`) taken directly from the repo's own `TRAIN_EVAL_SUTRAN_NDA.py`.

A synthetic-tensor smoke test (now standard practice before any real training run) caught a genuine architectural bug before it wasted training time: cross-attention's mask-broadcasting logic assumes decoder query length always equals encoder key length, which breaks during naive incremental autoregressive decoding. Fixed by matching the original repo's own approach — decode with a fixed full-window decoder input at every step (future positions padded, read out via the causal mask), not a dynamically-growing sequence. A related fix: prefix and suffix tensors must share one `window_size` (not independent max lengths), matching the original repo's own convention, for the same mask-broadcast reason.

Result: trained on Helpdesk, same split as A1/A2 (confirmed identical `dataset_split_hash`). **No published-number comparison exists for this pair** — SuTraN's own paper never evaluated Helpdesk (it used BPIC17/BPIC17-DR/BPIC19/BAC) — disclosed as a limitation rather than hidden. Validation-set mean normalized Damerau-Levenshtein similarity (autoregressive generation): **0.924**. Test-set: **0.816**.

**The val/test gap is now confirmed a THIRD time**, across a genuinely different objective (full-suffix generation vs. next-activity classification) and a genuinely different metric (DL-similarity vs. accuracy): A1 86.9%→72.9%, A2 81.8%→63.5%, A4 92.4%→81.6%. Three architectures, two objectives, two metric families, same dataset/split, same qualitative pattern. This has crossed from "worth watching" to "should be its own dedicated analysis" — see the updated open question.

New reusable infrastructure built along the way: `src/data/prefixes.py` gained `make_suffix_prefixes` (shared by A4/A5/B2, the same "one definition per objective type" pattern as A1/A2's next-activity prefixes), and `src/evaluation/suffix_metrics.py` implements normalized Damerau-Levenshtein similarity (unit-tested against hand-worked cases) — this is also the metric spec §8.8 calls for in the Phase 8 future-equivalence study, so it's already available when that phase needs it.

**A5 CRTP-LSTM — DONE.** No autoregressive decoding needed at all (unlike A4) — the paper's own "direct" mechanism: prefix fed as a **left-padded** sequence (opposite of A1/A2/A4's right-padding) to a bidirectional LSTM, so every output position sees the whole prefix via the backward pass regardless of prefix length, letting the model regress onto the entire suffix in one forward pass at both train and eval time. Fastest integration so far — reused A4's vocabulary/suffix-target encoding directly via import (`models.sutran.adapter`), adding only left-padded prefix encoding. Hyperparameters (`d_model=80`, `NAdam(lr=0.002)`, `ReduceLROnPlateau(patience=16)`, early-stop patience 24) taken directly from the repo's own `TRAIN_EVAL_CRTP_LSTM_ND.py`. Same activity-only scope decision as A4.

Result: same split as A1/A2/A4 (confirmed identical `dataset_split_hash`), converged fast (best checkpoint ~epoch 1, early-stopped at 25). No published-number comparison (same reason as A4). **0.917 validation / 0.816 test** mean normalized DL-similarity — remarkably close to A4's 0.924/0.816 despite a completely different architecture (direct BiLSTM vs. autoregressive Transformer decoder). **The val/test gap is now confirmed a FOURTH time** (A1 86.9%→72.9%, A2 81.8%→63.5%, A4 0.924→0.816, A5 0.917→0.816) — 4 architectures, 2 objectives, 2 metric families, one dataset/split, one consistent pattern. This is now a strong, well-replicated finding.

**A3 RLHGNN — DONE, first heterogeneous-GNN model, most up-front reading of any integration so far.** Read `main.py`, `build_graph.py`, `Train.py`, `model/model.py`, `MyDataset.py`, `data_process.py`, and `ProcessEventlog_one_graph.py` in full, plus fetched and read the actual arXiv PDF (2507.02690, not just the abstract), before writing any code — needed to resolve an ambiguity the repo's own CLI defaults left open (`Train.py` argparse default `num-epochs=50` vs. the paper's stated "100 epochs, early stopping after 10"; used the paper's number) and to confirm exactly what the RL/DQN structure-selection stage (`env_train.py`/`final_policy.py`) actually does before deciding to drop it.

**Scope decisions:** (1) skip RL/DQN graph-structure selection entirely, always use the paper's "Comprehensive" fixed graph (forward + backward + repeat_next edges, `action=3`/`build_Bidirect_complex_graph`) — justified by the paper's own ablation (Table V) showing this is the second-best fixed structure, within ~1 GMean point of the full RL policy, while being the richest of the four and keeping the paper's actual technical contribution (relation-specific GraphSAGE aggregation: LSTM for forward/backward, mean for repeat_next); (2) activity-only, same project-wide rule as A1/A2/A4/A5 — the original also embeds resource + two engineered/discretized timestamp features, all dropped. Unlike every other model in the roster, RLHGNN's graphs are **not padded to a fixed window** — one DGL heterograph per prefix, exactly as many nodes as the prefix is long, matching the original's own design; graph construction (including the `repeat_next` edge logic) was ported by hand from `build_graph.py` and verified against a hand-worked example before training. Architecture is a from-scratch reimplementation against the paper's equations and the repo's own `model/model.py` (**the repo has no LICENSE file at all** — confirmed again at integration time, still an open item). Also found and documented a paper/code discrepancy: the paper's prose describes the readout as focusing on "the current activity position" (implying the last node), but the actual code does `dgl.max_nodes(hg, 'h')` (max over every node) — replicated the code's real behavior, since that's what produced the paper's reported numbers.

Result: same split as A1/A2/A4/A5 (confirmed identical `dataset_split_hash`). Training converged fast and stably (best checkpoint at epoch 2, early-stopped at epoch 12 of a 100-epoch budget). **No published-number comparison exists for this pair** (RLHGNN's paper evaluates six BPI12/13/2020 logs, never Helpdesk) — disclosed, not hidden. **Best validation accuracy 86.4%**, but **test accuracy only 72.1% micro / 54.6% macro-across-k** — landing almost exactly on top of A1's 86.9%/72.9% despite a completely unrelated architecture family (heterogeneous GNN vs. Transformer). Per-prefix-length metrics show a sharp accuracy dip at k=1 not seen this sharply in the other models — plausibly an artifact of RLHGNN's very short (1-2 node) prefix graphs giving its GraphSAGE aggregators little structure to exploit, worth a closer look during Phase 5.

**The val/test gap is now confirmed a FIFTH time**: A1 86.9%→72.9%, A2 81.8%→63.5%, A4 0.924→0.816, A5 0.917→0.816, A3 86.4%→72.1% — five models, five architectures, two objectives, two metric families, one dataset/split, one relentlessly consistent pattern. A3 landing almost exactly on A1's numbers despite a totally unrelated architecture is about as strong as single-dataset evidence for genuine temporal distribution shift can get.

z_t extraction: `model.encode(hg)` returns the graph-level max-pooled node embedding (batch, 128), confirmed `(3, 128)` against the trained checkpoint — architecturally distinct from every other model in the roster (the only one that pools over the *whole* prefix graph symmetrically rather than reading out a designated last-position hidden state), flagged for the Phase 5 write-up.

**A6 LUPIN — DONE, first text-narrative/pretrained-LLM model.** Architecturally unlike anything else in the roster: encodes the entire running prefix as a natural-language "story" (one templated sentence per event, activity-only per this project's scope rule — a larger proportional cut than for any other model, since LUPIN's own contribution is precisely the rich attribute-to-text encoding being dropped), tokenizes with the pretrained `prajjwal1/bert-medium` checkpoint's own WordPiece tokenizer, fine-tunes the BERT encoder, and attaches one independent linear classification head per suffix position on the pooled `[CLS]` output — direct/non-autoregressive, same family as A5 CRTP-LSTM, but via K heads on one pooled vector rather than a recurrent per-timestep readout. Two vocabularies in play (BERT's own subword input vocab vs. this project's closed TRAIN-only output class vocab, reused directly from A4's `Vocab`) — a genuine architectural difference, not a bug, unique to this model.

**License:** LUPIN's source (`vinspdb/LUPIN`) is **CC BY-NC-SA 4.0** (non-commercial, share-alike) — `src/models/lupin/` kept isolated per this project's license-isolation policy (same handling as A7 MLMME's planned GPL-3.0 isolation).

A real old-checkpoint/new-library compatibility bug was caught by the now-standard pre-training smoke test: `prajjwal1/bert-medium` predates the modern `Auto*` registry convention, so `AutoModel`/`AutoTokenizer.from_pretrained(...)` both fail under `transformers` 5.15.0 — worked around with concrete `BertModel`/`BertTokenizerFast` classes. Compute-budget deviations from the repo (`batch_size=32` not 8, `max_token_length` capped at 48 not 512, `epochs` capped at 15 not 50) are measured, not guessed: at the repo's own settings one epoch took ~59 min on this project's CPU-only hardware; the tuned settings bring this to ~14 min/epoch. Also did **not** replicate a real checkpoint-selection bug found in the original repo's own training script (`best_model = model` keeps a live reference instead of a snapshot, so it silently saves the last epoch's weights regardless of which epoch actually had the best validation loss).

Result: same split as A1–A5 (confirmed identical `dataset_split_hash`). **A7 MLMME — DONE, the last Family A model, first (and only) adversarially-trained (GAN) one.** Fetched and read the actual SDM 2021 paper in full plus cloned and read the actual repo (`network.py`/`main.py`/`preparation.py`/`suffix.py`) before writing any code, since the exact GAN training mechanism was a genuine architectural question, not a footnote. Resolved: the generator (encoder+decoder, both plain 5-layer/200-hidden unidirectional LSTMs over one-hot event vectors, no embedding layer) and discriminator (same LSTM size + one Linear(200,1) per-timestep realism head) train **jointly from initialization** every mini-batch — no separate pretrain-then-adversarial-fine-tune phase, and no REINFORCE/policy-gradient: discrete sequences are handled via **Gumbel-softmax continuous relaxation** (label-smoothed+near-discrete for the "real" side, exponentially-annealed temperature for the generator's own "fake" side), with the generator update minimizing the sum of an adversarial "fool the discriminator" loss and the standard supervised cross-entropy loss (exactly the paper's Algorithm 1). Found and resolved two real paper/code discrepancies: (1) the paper's Eq. 4.1 states Softmax for the activity head, but the actual code applies an indiscriminate ReLU before cross-entropy — replicated the code's real behavior, per this project's established practice; (2) the reference repo's own generator-update step reuses an already-`.detach()`-ed fake-sequence tensor, which — combined with this project's activity-only scope removing the one output column (duration-time) that let gradient leak through in the original two-headed design — would make the adversarial loss a complete no-gradient no-op for the generator if replicated verbatim; this project deliberately does **not** replicate that specific `.detach()`, restoring genuine gradient flow from the discriminator into the generator's activity-prediction weights while still correctly detaching for the discriminator's own update. A synthetic-tensor smoke test explicitly asserted both halves of this (zero generator gradient after the discriminator-only update, nonzero after the generator's own adversarial update) before any real training was attempted — caught nothing further wrong, confirming the fix works as intended.

**A real environment constraint discovered during A7, not encountered by any earlier model**: this project's execution environment kills long-running background training processes at approximately the 60-minute mark regardless of health. A first attempt at a measured, disclosed 40-epoch budget (down from the paper's own impractical 500 epochs — ~135s/epoch measured, ~18.75 hours at 500) was killed mid-run at ~60 minutes while still actively improving its checkpoint, not crashing on its own.
